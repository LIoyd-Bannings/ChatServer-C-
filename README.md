# High-Performance Distributed Chat Server

这是一个基于 C++11 开发的高性能分布式聊天服务器。项目采用 `Muduo` 网络库作为核心网络层，使用 `MySQL` 进行数据持久化，并通过 `Redis` 的发布-订阅机制支持集群服务器间的消息通信。

本项目重点记录从一个基础 Demo 到较为成熟的高性能服务器的**性能优化与架构演进过程**的一小步。

## 🛠 技术栈
* **语言**: C++11
* **网络框架**: Muduo (Reactor 模型, Epoll + 非阻塞 IO)
* **数据库**: MySQL + **手写数据库连接池**
* **中间件**: Redis (Hiredis)
* **序列化**: JSON (nlohmann/json)
* **构建工具**: CMake
* **开发环境**: Linux

##  性能优化与架构演进 (Optimization Journey)

本项目经历了两个关键阶段的重构与优化，将系统从“不可用”状态提升至“高性能稳定”状态。

###  第一阶段：引入数据库连接池 (Connection Pool)

#### 1. 问题背景
在早期的短连接模式下，每次业务请求（如登录、注册、发消息）都需要经历 `TCP握手 -> MySQL认证 -> SQL执行 -> 关闭连接` 的全过程。
* **性能瓶颈**：在高并发压测下（10线程并发），Server 端大量的 CPU 时间消耗在握手和释放资源上。
* **现象**：
    * 有效吞吐量 (Valid QPS) 极低（< 10 QPS）。
    * 系统端口资源耗尽，出现大量 `TIME_WAIT`。
    * 客户端频繁收到连接超时或拒绝错误。

#### 2. 解决方案
自主实现了一个基于生产者-消费者模型的数据库连接池：
* **核心机制**：使用 `std::queue` 维护连接队列，通过 `std::mutex` 和 `std::condition_variable` 保证线程安全。
* **RAII 管理**：利用 `std::shared_ptr` 的**自定义删除器 (Custom Deleter)**，实现连接使用完后自动归还连接池，而非物理关闭，彻底消除了连接创建开销。
* **健壮性**：修复了 MySQL C API 在多线程下的全局初始化竞争 (`mysql_library_init`) 问题，以及拷贝构造导致的 Double Free 问题。

#### 3. 优化结果
* **DB 连接开销**：从 **100%** 降至 **0** (启动后全程复用)。
* **吞吐量**：在 100万请求压测下，Server 有效 QPS 稳定在 **700~800** (达到单机 MySQL 机械硬盘的 I/O 物理极限)。
但是，由于TCP粘包问题，json解析错误问题严重，超过一半以上json并没有被成功解析。

### 第二阶段：解决 TCP 粘包与并发安全 (Stability)

#### 1. 网络层：解决 TCP 粘包/拆包
* **问题**：在高吞吐量下（客户端发送速度 > 1万 QPS），Muduo 接收缓冲区出现严重的 TCP 粘包现象，导致 JSON 解析失败率高达 60% 以上，服务端频繁报错 `JSON Parse Error` 并断开连接。
* **解决**：设计并实现了 **Length-Header (长度头)** 应用层协议。
    * **协议格式**：`[4字节大端长度] + [JSON 数据 Body]`。
    * **处理逻辑**：服务端在 `onMessage` 中循环处理 Buffer，只有当缓冲区数据长度 >= 头部指定长度时才进行拆包与反序列化。
* **效果**：在 100万次高频请求下，**JSON 解析错误率降为 0**，数据传输可靠性达到 100%。

#### 2. 业务层：解决 Redis 客户端线程竞争
* **问题**：压测中服务器频繁出现 `free(): invalid pointer` 并崩溃。
* **排查**：`hiredis` 的 `redisContext` 上下文是非线程安全的。当多个业务线程同时调用 `subscribe` 或 `publish` 时，导致底层缓冲区内存损坏。
* **解决**：对 Redis 操作进行封装，引入 `std::mutex` 互斥锁，分离发布锁和订阅锁，确保同一时刻只有一个线程操作 Redis 上下文。
* **效果**：彻底修复了 Core Dump 问题，服务器在长时间高压测试下保持稳定运行。

##  最终性能压测报告 (Benchmark)

测试环境：本地回环网络，10 线程并发，累计发送 100万 条消息。

| 指标 | 1. 初始版本 (无连接池) | 2. 连接池优化版 | 3. 最终稳定版 (含 Redis + 协议修正) |
| :--- | :--- | :--- | :--- |
| **Server Valid QPS** | **< 10** (严重阻塞) | **~690** (MySQL 瓶颈) | **~1500** (Redis 缓存加速) |
| **DB Connect 开销** | 极高 (每次请求) | **0** (全程复用) | **0** |
| **错误率 (Error Rate)** | 极高 (超时/拒绝) | 高 (TCP 粘包错误) | **0% (无错误)** |
| **系统稳定性** | 频繁崩溃/断连 | 偶发解析失败 | **持续稳定运行** |

> **注**：
> * **~690 QPS**：对应业务逻辑为 `写 MySQL`（磁盘 IO 密集型），反映了硬盘写入的物理上限。
> * **~1500 QPS**：对应业务逻辑为 `写 Redis`（内存 IO 密集型），反映了在加锁串行化条件下的内存处理极限。

## 📂 核心代码说明
* `src/server/db/ConnectionPool.cpp`: 数据库连接池核心实现。
* `src/server/chatserver.cpp`: `onMessage` 回调中实现了解决 TCP 粘包的拆包逻辑。
* `src/server/redis/redis.cpp`: 封装了带有互斥锁保护的 Redis 操作。
